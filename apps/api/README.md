# apps/api

Fastify 5 + Drizzle + PostgreSQL 16. Контракти запитів і відповідей — у `@khronist/contracts`.

## Запуск

1. `docker compose -f infra/docker-compose.yml up -d` (Postgres 16 із `pg_trgm`, порт лише на `127.0.0.1`).
2. Скопіювати `.env.example` у `.env`.
3. `pnpm db:migrate`, потім `pnpm dev`.
4. `GET http://localhost:3000/health`: 200, якщо база відповідає, інакше 503 із `db: "down"`.

`infra/init.sql` виконується лише на порожньому томі Postgres. Для наявного тому: `docker compose -f infra/docker-compose.yml down -v` (стирає дані локальної бази).

## Тести

`pnpm test` не потребує Docker: схема перевіряється на вбудованому PGlite (WASM Postgres) із тими самими міграціями й розширенням `pg_trgm`. Тест `runtime.test.ts` запускає `node src/server.ts` без збирача, щоб зловити синтаксис, який Node не вміє стирати.

## Міграції

`pnpm db:generate` створює SQL у `src/db/migrations`. Перша міграція вручну починається з `CREATE EXTENSION IF NOT EXISTS pg_trgm`: Drizzle розширення не генерує, а індекси `gin_trgm_ops` без нього не створяться. Нові міграції після першої вручну правити не треба.

## Розгортання

Контракти віддаються сирим `.ts`, тож на хостингу (Railway) ставимо залежності всього монорепо й запускаємо `pnpm --filter @khronist/api start`. `pnpm deploy` і копіювання `node_modules` не використовувати: Node не стирає типи в `node_modules` і падає з `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`. Змінні `HOST=0.0.0.0` і `DATABASE_URL` задати у змінних середовища.

## Рішення по схемі

- Ідентифікатори прикладних таблиць — UUID v7 (генерує застосунок через `uuidv7`), тож сирий SQL має передавати `id` сам. Таблиці Better Auth (`user`, `session`, `account`, `verification`) мають текстові ідентифікатори й експортуються під цими іменами, як очікує адаптер.
- Підтверджені дані захищені: ланцюжок `documents → pages → regions → transcriptions → edits` має `ON DELETE RESTRICT`, каскад лише для рядків, слів і сутностей.
- Шифр сторінки: `pages.folio` і `pages.image_no` необов'язкові, але хоча б одне заповнене. Обидва унікальні в межах документа; NULL-значення можуть повторюватися. Разом сторінка з лише `folio` і сторінка з лише `image_no` для одного фізичного аркуша не розпізнаються як дублікат: це має вирішувати застосунок.
- `regions.page_id` необов'язковий: розширення може надіслати фрагмент без розпізнаного шифру.
- Координати — частки 0…1; `x + w` і `y + h` не більші за 1 із допуском 1e-6 на похибку float.
- Для регіону може бути лише одне активне розпізнавання (`queued`, `reading`, `normalizing`): подвійне надсилання не подвоює витрати на модель.
- `chunks.tsv` — обов'язкова колонка `tsvector`, заповнюється інгестією (`to_tsvector('simple', …)` через `sql`, текст плюс варіанти зі `synonyms`). Унікальність чанка — `(source_id, text_hash)`.
- Повнотекстовий пошук по `transcriptions.normalized_text` обслуговує індекс на виразі `to_tsvector('simple', normalized_text)`; запит має використовувати той самий вираз буквально.
- Відкрите питання дизайну: чи може бути кілька версій одного регіону зі статусом `verified`. Правило поки не закладене в схему.
- Таблиці Better Auth описані за документацією; звірити з `@better-auth/cli generate` під час підключення авторизації (версія 1.7) і за потреби додати міграцію.
- Колонки `timestamptz` повертаються як `Date`, а контракти очікують рядок ISO: перетворювати перед відповіддю.
- Локаль бази: `pg_trgm` і конфігурація `simple` залежать від `LC_CTYPE`. Перевірити нижній регістр кирилиці на проді (`select lower('Б')`).
