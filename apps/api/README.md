# apps/api

Fastify 5 + Drizzle + PostgreSQL 16. Контракти запитів і відповідей — у `@khronist/contracts`.

## Запуск

1. `docker compose -f infra/docker-compose.yml up -d` (Postgres 16, порт лише на `127.0.0.1`).
2. Скопіювати `.env.example` у `.env`.
3. `pnpm db:migrate`, потім `pnpm dev`.
4. `GET http://localhost:3000/health`: 200, якщо база відповідає, інакше 503 із `db: "down"`.

## Тести

`pnpm test` не потребує Docker: схема перевіряється на вбудованому PGlite (WASM Postgres) із тими самими міграціями й розширенням `pg_trgm`. Тест `runtime.test.ts` запускає `node src/server.ts` без збирача, щоб зловити синтаксис, який Node не вміє стирати.

`pnpm --filter @khronist/api smoke` проганяє читання проти запущеного сервера зі справжнім PostgreSQL і `postgres-js`, бо PGlite не ловить усіх помилок драйвера. Сервер має працювати з `LLM_FIXTURES=1`. У CI це задача `runtime`.

## Міграції

`pnpm db:generate` створює SQL у `src/db/migrations`. Перша міграція вручну починається з `CREATE EXTENSION IF NOT EXISTS pg_trgm`: Drizzle розширення не генерує, а індекси `gin_trgm_ops` без нього не створяться. Нові міграції після першої вручну правити не треба.

## Розгортання

Контракти віддаються сирим `.ts`, тож на хостингу (Railway) ставимо залежності всього монорепо й запускаємо `pnpm --filter @khronist/api start`. Міграції застосовує `pnpm db:migrate`; йому потрібен лише `DATABASE_URL`. `pnpm deploy` і копіювання `node_modules` не використовувати: Node не стирає типи в `node_modules` і падає з `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`. Змінні `HOST=0.0.0.0` і `DATABASE_URL` задати у змінних середовища.

Сервіс і база на Railway описані в `.railway/railway.ts`: збірка Railpack, міграції як pre-deploy, перевірка `/health`, деплой `main` лише після зеленого CI. Зміни застосовуються з кореня репозиторію через Railway CLI: `railway login`, `railway link`, `railway config plan`, `railway config apply`. Ключі (`ANTHROPIC_API_KEY`, `GOOGLE_API_KEY`) у файлі позначені `preserve()` і задаються в Railway, а не в репозиторії.

- Власний домен конфігурація не реєструє: `api.khronist.org` додається в дашборді Railway (Settings → Networking), записи CNAME і TXT — у Cloudflare в режимі «DNS only». Після цього домен дописується в `domains` сервісу в `.railway/railway.ts`, і `railway config plan` має показати відсутність змін (`pull` не використовуємо: він перезаписує файл згенерованим кодом).
- На Windows SDK `railway` перевіряє версію CLI запуском `process.env._ || "railway"` без оболонки й не бачить обгортку `railway.cmd` з npm, тому падає з «requires Railway CLI 5.42.1 or newer» навіть на новому CLI. У PowerShell перед `railway config` вказати справжній файл: `$env:_ = "$(npm root -g)\@railway\cli\bin\railway.exe"`.

## Рішення по схемі

- Ідентифікатори прикладних таблиць — UUID v7 (генерує застосунок через `uuidv7`), тож сирий SQL має передавати `id` сам. Таблиці Better Auth (`user`, `session`, `account`, `verification`) мають текстові ідентифікатори й експортуються під цими іменами, як очікує адаптер.
- Підтверджені дані захищені: ланцюжок `documents → pages → regions → transcriptions → edits` має `ON DELETE RESTRICT`, каскад лише для рядків, слів, сутностей і записів `recognitions` (останні видаляються разом із регіоном).
- Шифр сторінки: `pages.folio` і `pages.image_no` необов'язкові, але хоча б одне заповнене. Обидва унікальні в межах документа; NULL-значення можуть повторюватися. Разом сторінка з лише `folio` і сторінка з лише `image_no` для одного фізичного аркуша не розпізнаються як дублікат: це має вирішувати застосунок.
- `regions.page_id` необов'язковий: розширення може надіслати фрагмент без розпізнаного шифру.
- Координати — частки 0…1; `x + w` і `y + h` не більші за 1 із допуском 1e-6 на похибку float.
- Для регіону може бути лише одне активне розпізнавання (`queued`, `reading`, `normalizing`): подвійне надсилання не подвоює витрати на модель.
- `chunks.tsv` — обов'язкова колонка `tsvector`, заповнюється інгестією (`to_tsvector('simple', …)` через `sql`, текст плюс варіанти зі `synonyms`). Унікальність чанка — `(source_id, text_hash)`.
- Повнотекстовий пошук по `transcriptions.normalized_text` обслуговує індекс на виразі `to_tsvector('simple', normalized_text)`; запит має використовувати той самий вираз буквально.
- Відкрите питання дизайну: чи може бути кілька версій одного регіону зі статусом `verified`. Правило поки не закладене в схему.
- Таблиці Better Auth описані за документацією; звірити з `@better-auth/cli generate` під час підключення авторизації (версія 1.7) і за потреби додати міграцію.
- Колонки `timestamptz` повертаються як `Date`, а контракти очікують рядок ISO: перетворювати перед відповіддю.
- Локаль бази: `pg_trgm` і конфігурація `simple` залежать від `LC_CTYPE`. Перевірити нижній регістр кирилиці на проді (`select lower('Б')`).

## Розпізнавання (`/v1/recognitions`)

- `POST /v1/recognitions` перевіряє тіло (рамка в межах зображення, рядки шифру до 64 символів без керуючих, `image` 1…100000, посилання на портал лише `http(s)` без логіна й лише з хостів `*.gov.ua` та `searcharchives.net.ua`), що зображення справді PNG (сигнатура, заголовок, кінцевий блок `IEND`, не більше 7 МіБ, 8000 px на сторону і 50 Мпк; перші два ліміти походять від Claude API) і що `imageHash` дорівнює SHA-256 його байтів (інакше кеш можна було б отруїти чужим хешем). Далі знаходить або створює документ, сторінку й регіон за хешем зображення.
- Якщо для регіону вже є транскрипція, повертає `cached` і новий запис розпізнавання, навіть коли ридер недоступний. Якщо читання вже триває, повертає той самий `recognitionId`. Інакше резервує місце в черзі, створює запис `queued`, ставить задачу й відповідає 201. Після вставки ще раз перевіряє кеш: так закривається вікно гонки, коли інший запит устиг дочитати фрагмент.
- `GET /v1/recognitions/:id` повертає стан і, коли готово, повну транскрипцію.
- `GET /v1/recognitions/:id/events` віддає SSE: `progress`, `line`, `done` або `failed`. Для запису, що ще виконується, потік одразу повідомляє поточний стан (зокрема `queued`), далі події надходять наживо, для завершеного повторюються з пам'яті (хвилину після завершення) або будуються з бази. Кожні 15 с надсилається `: ping`. Потік закривається після `done` або `failed`, через 5 хвилин (тоді клієнт перепитує `GET /v1/recognitions/:id`), при розриві з'єднання та при зупинці сервера. Клієнт має сам закривати потік на `done` і `failed`, інакше `EventSource` перепідключатиметься кожні 3 с. Події не мають `id`, відновлення з `Last-Event-ID` не підтримується.
- Задача: читання (ліміт 30 с), нормалізація (20 с), збереження в одній транзакції. Таймаут скасовує ридер через `AbortSignal`. Результат ридера й нормалізатора перевіряється до запису (рамки, послідовні `idx`, межі сутностей), некоректний результат дає `read_failed` або `normalize_failed`, а не `save_failed`. Кожне оновлення статусу працює лише для активних записів: якщо запис закрито ззовні (перезапуск, очищення), задача не воскрешає його, а відкочує транзакцію. Повторне читання вже прочитаного регіону додає нову версію транскрипції.
- Запис, що завис активним понад 10 хвилин, закривається як `read_failed` при наступному запиті на цей фрагмент. Після перезапуску сервера всі активні записи стають `failed` із кодом `restarted`; це припускає один екземпляр сервера (див. «Розгортання»).
- Черга: до 50 задач у роботі й очікуванні, місце резервується до першого `await`, тож ліміт точний. Понад ліміт: 429 `too_many_requests` із `Retry-After: 60`.
- Тіло запиту: 1 МіБ за замовчуванням, 12 МіБ лише на `POST /v1/recognitions`.
- Зупинка сервера: закриваються відкриті потоки, задачі, що чекають у черзі, не запускаються (після старту їх закриє відновлення з кодом `restarted`), поточні завершуються до 10 с, повторний сигнал завершує процес одразу.

### Що працює справді, а що ні

Читання справжнє: якщо задано `ANTHROPIC_API_KEY`, працює ридер `services/htr/vision.ts` за промптом `htr_vision` (чернетка v1), `/health` показує `htr: "vision"`. Модель і глибина задаються `HTR_MODEL_PRIMARY` (стартово `claude-sonnet-5-5`) і `HTR_EFFORT` (`medium`); порівняння — у `docs/htr-feasibility.md`. Кожне читання пише в лог модель, токени й час. Коли модель повертає непридатну відповідь, запит повторюється один раз; потім, або при помилці API, вмикається `HTR_MODEL_FALLBACK`, якщо заданий. Весь цей шлях укладається в ліміт 30 с: коли резерв заданий, основна модель разом із повтором має 20 с, решта лишається резерву. Обірвана за лімітом токенів відповідь не повторюється, бо вийшла б така сама, а одразу йде на резерв. Слова кожного рядка мають збігатися з його текстом, інакше позначки непевності були б неправдивими, тож така відповідь вважається непридатною. У `transcriptions.reader` записується модель, яка справді відповіла, зокрема резервна. Основна модель — Claude, резервна — Gemini: `HTR_MODEL_FALLBACK=gemini-3.6-flash` разом із `GOOGLE_API_KEY`. Резерв без ключа зупиняє сервер на старті, щоб не здаватися робочим, тому в `.env.example` змінна порожня. Для Gemini глибина завжди `low`: уже `medium` дає 25–35 с. Він отримує спільний промпт і додаток `htr_vision/gemini.md`, бо без нього впевнено вигадує імена. `HTR_URL` (трек B) поки не реалізовано: непорожнє значення зупиняє сервер на старті, щоб він не здавався ввімкненим.

Безплатний ключ Gemini придатний лише для розробки: 20 запитів на добу на модель, а умови забороняють надсилати персональні дані в безплатний сервіс і дозволяють для користувачів із ЄЕЗ, Швейцарії та Британії лише платний. На проді для резерву потрібен ключ із білінгом.

`LLM_FIXTURES=1` вмикає замість цього ридер, який повертає одну демонстраційну запис незалежно від зображення (`htr: "fixture"`). У `NODE_ENV=production` цю змінну заборонено. Без ключа основної або резервної моделі й без фікстур ридера немає: нові фрагменти дають 503, `htr: "down"`. Нормалізація досі заглушка: `normalizedText` дорівнює сирому тексту, сутності порожні, бо промптів `normalize` і `entities` ще немає. Перш ніж підключати справжній ридер до бази, де бували фікстури, стерти фікстурні транскрипції: кеш віддає їх як справжні.

### Доступ для гостей

- `POST /v1/recognitions`: `GUEST_RECOGNITIONS_PER_DAY` (60) запитів на добу з однієї адреси, для IPv6 — з однієї підмережі /64. Понад ліміт: 429 `too_many_requests` із `Retry-After` у секундах до скидання. Рахуються всі запити, зокрема з кешу й некоректні: лічильник спрацьовує до читання тіла, тож завеликий запит не витрачає пам'ять. Читання стану й потоку подій не обмежені.
- Лічильники живуть у пам'яті процесу й скидаються при перезапуску. Для пакетної обробки поки що піднімати змінну; після входу й API-ключів обхід ліміту буде за ключем.
- Адреса клієнта береться із заголовка `CLIENT_IP_HEADER`, якщо він містить коректну IP-адресу, інакше з адреси з'єднання. На Railway це `x-real-ip`: його виставляє edge-проксі й замінює копію клієнта, а кількість проксі перед сервісом не фіксована, тож рахувати кроки в `X-Forwarded-For` ненадійно. Без проксі змінну лишати порожньою, інакше клієнт підставить будь-яку адресу.
- `CORS_ORIGINS`: точні origin через кому, зокрема `chrome-extension://<id>`. Порожнє значення не дозволяє нікого, а `*`, маски й кінцевий `/` зупиняють сервер на старті, бо запити йдуть з `credentials`. Заголовки дозволу є і на помилках, і на потоці подій.

### Обов'язково до публічного запуску

- Загальний бюджет читання. Ліміт за IP (див. «Доступ для гостей») не зупинить багато адрес одразу, тому на ключі Anthropic має стояти ліміт витрат.
- Довіра до шифру. Регіон знаходиться за хешем зображення, і шифр та рамку фіксує перший, хто надіслав цей фрагмент; усі наступні читачі побачать його шифр. Хто завгодно може надіслати чужий скан із вигаданим шифром, хоча сам хеш підробити не вдасться. Поки немає входу, шифр слід вважати непідтвердженим: коли користувач підтверджує транскрипцію, шифр має підтверджуватися знову, а не братися з регіону. Це потребує рішення команди.
- `GET /v1/recognitions/:id` публічний і віддає ім'я автора й того, хто підтвердив, анонімним відвідувачам. Це рішення про приватність.

### Відомі обмеження

- Один екземпляр сервера. Якщо Railway запустить нову версію, поки стара ще працює (перекриття деплоїв), нова при старті позначить активні записи старої як `restarted`; стара не воскресить їх завдяки охороні статусу, але користувачі побачать помилку. Вимкнути перекриття деплоїв у налаштуваннях Railway.
- У `sql`-шаблонах Drizzle не передавати `Date` напряму (`${new Date()}`): `postgres-js` серіалізує такий параметр неправильно, а PGlite у тестах цього не ловить. Для порівняння дат використовувати оператори над колонкою (`lt`, `gt`). Виявлено лише запуском справжнього сервера через `postgres-js`.
- У service worker розширення MV3 немає `EventSource` і він не вміє надсилати заголовки авторизації: для потоку подій у розширенні використовувати `fetch` зі стрімінгом.
- `attempts` дорівнює 1 для прочитаного запису й 0 для відповіді з кешу: повторних спроб читання одного запису поки немає.
- Підказки (`hints`) ураховуються лише при першому читанні фрагмента; кеш не розрізняє підказки.
